# /goal：从零实现 L2-hybrid 实机校准参考

在当前 Linux 服务器的空白工作区，从公开上游正式 release 开始，独立实现一版单实例 L2-hybrid KV cache 系统。实际完成代码、部署、正确性验证、轻量实验及可复跑证据，作为未来模拟器的校准参考。需求以本文件及同目录 ACCEPTANCE.md 为准；SOURCES.md 提供公开来源。

接收环境不具有其他项目的源码、文件组织、实验名称、数据集或模拟器。不要查找、恢复或依赖它们。服务器端不实现、不安装、不运行、不适配模拟器；其验收完全由真实系统的测试与测量完成。这里的“从零”指独立建立本项目并开发必要扩展，仍应复用 vLLM/LMCache 的成熟执行机制，不重写整个推理引擎。

## 目标范围

- 单台服务器、单 GPU、单 vLLM 实例，使用 LMCache 集成外部 KV 保留；固定 vLLM native 请求调度。
- 使用任务启动时核实的 vLLM、LMCache 最新正式 release tag。交接核验的候选为 vLLM v0.29.0、LMCache v0.5.5；开始时核对公开发布入口，冻结实际 tag、完整 SHA 和构建依赖，开发期间不自动升级。不使用 nightly、RC 或其他产品的发布标签代替。
- 优先使用服务器已具备的 Qwen2.5-7B 系列 dense/GQA 模型；记录模型、tokenizer、dtype 和实际 KV layout。若模型不可用，说明所选替代及测量范围；不能用极小模型测试代替目标规模验证而不标注。
- 本轮不开发新的请求调度、主动预取/Promotion、压缩、多实例、跨机路由或完整 DAG 调度。不要求放置规则必须产生正收益；完成条件是可信、可测量、可重建。
- 由你选择新项目的简洁目录和模块结构；没有从其他项目继承的组织约束。将阶段计划、运行方法与验收状态保存在这个新项目内。

## 拓扑与语义

目标物理路径为 HBM ↔ {DRAM ∥ CXL}。“L2-hybrid”是本系统名称，不自动对应 LMCache 内部的层号。

1. DRAM/CXL 是平级、容量受限的长期保留池。CXL→HBM 的 payload 不经过普通 DRAM 暂存；CPU 控制、映射和同步仍可存在且需计费。明确反向 STORE 的真实路线与中转。
2. 同一完整逻辑 KV 版本在两池间只有一个稳定归属；HBM 可保有额外副本。只发布已完成、不可变的 KV 区间；活动尾块未定义版本/COW 时不能共享。一写多读指内容发布与多个读者，不预设只有一条物理写流。
3. 两池访问 HBM 时使用真实共享链路和 copy engine；测量同向争用、双向复制、计算重叠，不人为给每池各分一份独立满速带宽，也不假定所有读写都串行。
4. 上游 DAX adapter 的 CPU L1 暂存路径不自动满足本目标。先核实 GPU 是否能够直接从真实 CXL backing 复制数据，给出内存归属、API/地址、调用路径和内容往返证据。DAX mmap 成功、两个普通内存池或人为 sleep 不构成验证。
5. 硬件不能实现该路线时，保留阻塞证据并完成 DRAM 参照及不依赖硬件的代码/测试，明确未完成项。仿真后端只能验证逻辑，串行暂存只能作为另一条诊断路径；改变目标拓扑须向用户说明并确认。

## 开发顺序与基本实现

先核实硬件、驱动/torch/CUDA/原生扩展 ABI，建立独立环境并完成纯 vLLM GPU smoke；随后打通 LMCache DRAM 路径，再实现平级 CXL 路径和共同目录/状态管理。

优先采用 LMCache MP 集成，显式核对实际 connector 模块、源文件和运行路径，不依靠同名类或 pip 版本字符串判断。以选定 tag 的真实接口为准；尽量让扩展集中在 LMCache 后端、必要的 connector glue 和观测代码，避免无必要修改 scheduler 核心。

首版放置规则确定为：
- 查询先利用可用 HBM 前缀；需要外部恢复时查唯一保留目录，按真实归属读取。
- 新对象优先放 DRAM，DRAM 满则使用 CXL；两池均满时先淘汰 CXL 池内合法 LRU 对象，为新对象在 CXL 腾空间。没有合法 victim 则明确拒绝/等待，不能越过 pin 或预约约束。
- 既有对象不因重复保存产生第二份长期副本。命中更新 recency；同时间以稳定对象 ID 破同分。
- 这个规则只是最小 DRAM-first 基线，不保证 DRAM 始终保存最热内容。首版不迁移驻留对象。
- 保存选址与 victim 选择必须能够通过策略实现/配置替换；分配、容量、引用保护、异步完成和发布由共同运行时负责。用强制选池测试验证边界即可，不开发复杂热度公式。
- 记录真实保存触发时机、回收粒度、LMCache chunk/vLLM block 映射和 output KV 保存范围；不要为方便比较而隐式改变原生机制。

## 正确性与可观测性

按照 ACCEPTANCE.md 验证每条命中/恢复路径、容量压力回收、重复引用、异步保护、取消/失败和结束后 drain。必须做真实模型计算与 KV 内容校验，不能以 metadata 命中或输出预录 token 代替。

提供可开关的结构化事件和 Perfetto 可读 timeline，关联 request、batch、transfer、逻辑 KV 版本和物理区间。区分请求等待、目标预约、CPU 提交、设备 DMA、完成观察、scheduler 采纳、缓存可用和首次计算。给出事件发生处时间戳及跨 CPU/GPU/进程的时间边界，不用日志落盘时间替代。

要能够回答：某请求等哪一个条件、哪次读写挡住了它、数据已复制完为何尚不能计算、回收是否因已有副本而省去 STORE。不能将所有等待记为 DMA，也不能通过每步强制同步破坏正常异步行为后声称完成性能校准。

## 轻量测量

从零实现确定性输入生成器和运行入口，不需要外部数据集：
- 无共享前缀；
- 固定长前缀配不同后缀，重复访问；
- 活动请求可容纳、闲置保留内容有容量竞争；
- 小规模并发/突发及空闲后的再次访问。
这些是机制负载，不宣称代表完整生产场景。保存原始文本、实际 token IDs、种子、到达与输出参数。多轮模式共享新会话到达与思考时间样本，后续请求由本配置上一轮实际完成加思考时间触发；不能固定所有轮次实际到达。若采用模型生成历史，各请求的缓存 key 必须基于真实输入。

对照至少包含 HBM-only、HBM+DRAM、HBM+DRAM/CXL；同一版本、模型、实际 HBM KV 块预算及调度设置，区分新增保留容量与相同容量下放置规则的影响。

分别测量两池的读/写，小中大实际复制规模，若干 prefill、decode 上下文和 batch 形状，以及读读、读写、计算复制重叠。采样范围按本机容量与应用形状选择。冷启动、触页/注册和稳态分开；分配、hash/lookup、策略、IPC、gather/scatter、CPU 提交/轮询、DMA、完成采纳和输出处理尽量覆盖。无法单独识别的开销注明归属或缺口，不能直接记零；重叠费用不能串行重复相加。

最小实验先小后大，每条设超时并保留失败；默认关键服务对照做3次独立进程重复并轮换顺序。保留 trace-off 性能参照，重 profiler 只用于结构解释并注明扰动。不要无界扫描参数或为制造 Placement 收益调慢某条路径。
